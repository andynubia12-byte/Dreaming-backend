## 1. 接入顺序与边界

推荐流程：读取 `bootstrap` → 选择并冻结完整模型 profile → 创建实验 → 提交一条消息 → 订阅该 run 的 SSE → 在 `answer_complete` 显示已保存答案 → 在 `run_complete` 结束执行状态 → 需要时读取 detail/memory/wire。重连只重放事件；不要因断线重新提交新提问。

HTTP 前缀为 `/workbench`，原默认工厂端口为 `8791`（历史值，新包默认 `8794`）。示例地址 `http://127.0.0.1:8794` 仅说明地址形状，不声明服务正在运行。

| 约束 | 实际实现 |
| --- | --- |
| 服务边界 | 仅绑定 `127.0.0.1` / `localhost` / `::1`；不是远程、多用户后端 |
| 本地访问检查 | `Host` 必须是上述主机加实际端口；IPv6 使用 `[::1]:端口`。若有 `Origin`，必须精确等于 `http://` + `Host`；`Sec-Fetch-Site: cross-site` 被拒绝 |
| 鉴权 | 没有独立 HTTP Bearer、登录、用户权限或必需 cookie；缺省 `Origin` 可通过。模型凭据属于出站供应商认证，与本地接口鉴权不同 |
| 浏览器接入 | 同源页面可用。无 CORS / OPTIONS 支持，另一个端口也是不同 origin；不能假设独立前端开发端口可直接跨域调用 |
| POST 请求体 | `Content-Type: application/json`；有效 `Content-Length` 为 1–33554432 字节；拒绝 `Transfer-Encoding`、重复 JSON 字段及 NaN/Infinity。多数业务对象拒绝未知字段 |
| 返回 | JSON 为 UTF-8；普通响应 `Cache-Control: no-store`。业务错误为 `{"error":"安全错误描述"}`；不保证返回内部异常细节 |
| 数据 | bootstrap、session、memory、SSE 与 wire 都可能包含摘要/问题/证据全文，虽然没有 API Key 明文。它们仍是私有工作区数据 |

没有统一的 `/api` 前缀，也没有 `PATCH`/`PUT` 更新接口。方法不支持时由 Python 基础 handler 处理，不能假定是 JSON 405。下表和 OpenAPI 只描述支持的调用方式。

## 2. 核心 HTTP 清单

表内状态码是成功码；同步仅指 handler 是否等待本地操作完成，并不保证不会调用供应商。

| 方法和实际路径 | 请求 / 返回核心形状 | 执行与成功码 |
| --- | --- | --- |
| `GET /workbench/bootstrap` | 无 body → `{profiles, credential_status, protocol_migrations, memories, snapshots, defaults, sessions, batches, server_time, capabilities}` | 同步本地读取，200 |
| `GET /workbench/models` | → `{profiles, credential_status, protocol_migrations}` | 同步，200 |
| `POST /workbench/models` | `{profile, label?, api_key?}` → `{profile, credential_status}` | 按 profile.id 新增或覆盖，200；无模型调用 |
| `DELETE /workbench/models/{model_id}` | 无 body → 同 models 列表返回 | 同步，200 |
| `POST /workbench/models/test` | `{model_id}` **或** `{profile, api_key?}` → 连接结果 | 同步等待一次合成模型请求，200 |
| `POST /workbench/models/discover` | `{model_id}` **或** `{base_url, auth?, api_key_env?, api_key?}` → `{ok, models:[{id}], http_status, url, error, message, elapsed_seconds}` | 同步上游 GET models，200 |
| `POST /workbench/sessions` | 新实验 `{model,memory,retrieval?,summary?,title?}`；继续实验 `{continue_from,...可选覆盖}` → `{session}` | 同步创建，201 |
| `GET /workbench/sessions/{session_id}` | → `{session,messages,memory,runs}` | 同步，200 |
| `POST /workbench/sessions/{session_id}/chat` | `{request_id,message}` → `{run_id,run,reused}` | 异步接受，202 |
| `POST /workbench/sessions/{session_id}/rename` | `{title}` → `{session}` | 同步，200 |
| `DELETE /workbench/sessions/{session_id}` | → `{ok:true,id,deleted:true}` | 同步软删除，200 |
| `GET /workbench/sessions/{session_id}/memory` | → `{text,version,present,chars,published_at,now_max}` | 同步读取，200 |
| `GET /workbench/runs/{run_id}` | → `{run}` | 同步，200 |
| `GET /workbench/runs/{run_id}/events?after=0` | SSE，详见第 5 节 | 持续连接，200 |
| `GET /workbench/runs/{run_id}/wire` | → `{run,wire_events}` | 同步，200 |
| `GET /workbench/runs/{run_id}/artifacts` | 与 `/wire` 相同返回；不是全部产物下载接口 | 同步，200 |
| `POST /workbench/batches/plan` | `{suite,summary?,previous_id?}` → plan | 同步规划，无模型调用，200 |
| `POST /workbench/batches` | 同 plan 请求 → `{batch}` | 重新规划后异步执行，202 |
| `GET /workbench/batches/{batch_id}` | → `{batch,manifest,results}` | 同步，可返回部分结果，200 |
| `GET /workbench/batches/{batch_id}/results/{case_id}` | → `{result,wire_events,summary}` | 同步，200 |
| `GET /workbench/batches/{batch_id}/report` | HTML `comparison.html` | 同步，200 |
| `POST /workbench/batches/{batch_id}/resume` | `{concurrency:1..16}` → `{batch}` | 本地准备后异步续跑，202 |

`bootstrap.sessions/batches` 是简要索引，不是完整详情。没有单独 `GET /sessions` / `GET /batches` 列表端点；没有单独 `/continuefrom` URL。

常见错误：400 参数/JSON/profile 不合法；403 本地同源检查失败；404 路由或资源不存在（报告/案例尚未生成也会 404）；409 忙锁、幂等键冲突、来源变化或禁止覆盖配置；413 请求体为空/非正/过大；415 非 JSON；500 本地未归类失败。无效 `Content-Length` 文本为 400。模型池未知 ID / 内置项删除是 400，而不是 404。POST `/models/discover` 的内部校验/上游失败通常封装为 HTTP 200 的 `ok:false`。

创建没有 `Location` 头。202 只说明已登记任务，最终成功须看 run/batch/案例状态。后台上游 401/429/5xx 不会把已返回的 202 改成这些状态码。

## 3. Profiles、凭据与消息角色

三个角色分别配置：`model` 是 MAIN 主回答；`retrieval.profile` 是检索 Agent；`summary.profile` 是选定引擎的独立摘要角色。三者都使用同一 Responses 客户端能力，角色独立，保存会话后使用脱离模型池后续编辑的配置快照。池内 profile 的 `label` / `builtin` 是目录元数据，创建会话时会移除。profile 不是只传一个模型 ID；会话的 `model` 必须是完整对象。

最小 profile 必需字段为 `id, model, base_url, api_format, parameters`，API Key 认证还必须有 `api_key_env`。`id` 是最长 80 个 ASCII 字符的短标识，首字符为字母或数字，后续允许字母、数字、`_ . -`。`api_format` 只能是 `responses`，新请求不接受 Chat Completions。`base_url` 是无凭据、query、fragment 和空白的 HTTP(S) 地址；未带 `/responses` 时追加该路径，拒绝 `/chat/completions`。订阅地址只允许下面示例的固定地址或其 `/responses` 形式。

**没有 `credentialsref` / `credentials_ref` 字段。** 真实凭据引用是：

- `auth` 缺省/`api_key`：`api_key_env` 为服务端环境变量名；显式保存 `api_key` 后由服务端存本机 Keychain，并返回 `WORKBENCH_POOL_KEY_…` 形式的环境引用。Key 不进入正常 profile 返回；旧会话引用在池编辑/删除后保留。
- `auth:"codex_subscription"`：实际请求时读取订阅认证，profile 无需 `api_key_env`，禁止上传 `api_key`。`credential_status.available:null` 是未检查，不代表认证无效。

允许的参数为 `temperature`、`top_p`、`service_tier`、`parallel_tool_calls`、`max_output_tokens`、`max_tool_calls`、`token_limit_field`、`reasoning`、`text`。约束见 OpenAPI；`temperature:null` 明确不发送温度，省略则使用当前调用默认值。`reasoning.effort` 支持 `none/minimal/low/medium/high/xhigh/max`；`none` 保留并发给供应商，不能替换成 high；省略 effort 是供应商默认。供应商不支持时直接报错，不自动删参数、换平台或换协议。`service_tier` 仅接受 `default/flex`，不支持 Fast/priority；示例省略该参数。

下列示例显式使用 **Sol/high，无 Fast**，仅演示一种合法订阅profile，不是v1主聊天或检索必须使用Sol。开发子Agent的Sol/high偏好与产品模型配置分开。当前默认主池ID是 `deepseek-pro`，检索与summary默认取 `deepseek-flash`；新工具可按各角色选择任意受支持profile。即使关闭summary，创建时仍解析其profile，因此示例也填写disabled summary的profile。本文没有改动默认值。

主聊天的消息输入是单一 `message` 字符串，不能通过 HTTP 提交 `role`、任意 `messages`、system 提示或 tool 结果。当前上游主请求默认是 `system`（完整记忆、当前 session 的近期对话和系统规则）+ `user`（带本地消息 ID/发送时间的当前问题）；近期对话嵌在 system 文本，不是客户端可提交的历史消息数组。检索角色也有独立 system/user 上下文。工具轮使用 assistant 原生 function_call 与 function_call_output，保留所需 reasoning 项，统一通过 Responses 编码；不使用 developer 代替 system，不使用 `previous_response_id`。不得把内部 assistant/tool 交接伪装成用户消息。

`/models/test` 使用无个人记忆的 `system: Reply OK` 与 `user: Hi`，最多一次模型请求，超时取 profile 与 30 秒的较小值；返回 `ok/category/http_status/protocol_outcome/finish_reason/error/message/response_sample` 及 test_id、fingerprint、耗时、请求数、产物相对位置。`ok:true` 仅代表基础流式回答通过，不保证工具、JSON、长上下文或摘要兼容。`/models/discover` 最多等待 15 秒，上游 GET `/models`，不保存配置；订阅 catalog 返回 `unsupported`，需手填模型名。本文未执行这两个接口。

## 4. 可调用的 v1 只读接入示例

下面是 `POST /workbench/sessions` 的合法 JSON 形状。用经 8788 方法生成的**完整摘要**替换占位文本；不要只传摘要路径或片段。此例在兼容的本地服务与有效订阅环境中可提交，本归档不代为发送。

```json
{
  "title": "虚构项目的v1只读会话",
  "model": {
    "id": "codex-sol-high",
    "model": "gpt-6.1-sol",
    "base_url": "https://chatgpt.com/backend-api/codex",
    "api_format": "responses",
    "auth": "codex_subscription",
    "parameters": {
      "temperature": null,
      "reasoning": {"effort": "high"},
      "max_output_tokens": 32000
    }
  },
  "memory": {
    "mode": "context",
    "text": "【占位：传入经8788方法生成的完整摘要。此处不是实际个人记忆。】",
    "enabled": true
  },
  "retrieval": {
    "enabled": true,
    "profile": {
      "id": "codex-sol-high",
      "model": "gpt-6.1-sol",
      "base_url": "https://chatgpt.com/backend-api/codex",
      "api_format": "responses",
      "auth": "codex_subscription",
      "parameters": {
        "temperature": null,
        "reasoning": {"effort": "high"},
        "max_output_tokens": 32000
      }
    }
  },
  "summary": {
    "enabled": false,
    "profile": {
      "id": "codex-sol-high",
      "model": "gpt-6.1-sol",
      "base_url": "https://chatgpt.com/backend-api/codex",
      "api_format": "responses",
      "auth": "codex_subscription",
      "parameters": {
        "temperature": null,
        "reasoning": {"effort": "high"},
        "max_output_tokens": 32000
      }
    }
  }
}
```

这里“只读”指 8788 输入摘要及正式来源不被此会话维护改写；聊天仍会写私有 chat_log、run 与请求记录。`retrieval.enabled=true` 允许主模型委托检索，是否调用取决于主模型；并非每轮保证检索。

**summary 与 source 是两条独立输入线。** 自定义 `memory.text` 决定常驻摘要全文；它不会导入原文、指定数据库，也不会宣称已核验为结构化 claims。当前 `create_session` 总是 `need_history=True`：对这种自定义文本，会从服务端当前 `source.db_path` 创建原文快照，再复制 `history.sqlite` 到新 workspace 的私有 DB，保留原始 chat#N，清空该副本的维护队列。即便 memory.mode 为 none、检索关闭也会冻结历史供日后开关使用。若选的是批准的 snapshot，则可以使用该 snapshot 对应历史。

因此，传入的 8788 摘要必须与操作者确认的 source 历史相配；HTTP 没有 source_db/source_id 任意选择字段，也不自动证明二者来自同一历史。`history_snapshot_id` 返回本次历史快照 ID；不是摘要方法版本。工作台不写正式 source，但新会话的私有库会追加当前对话，检索也可看到该分支此前的对话。检索严格限定到本轮 now 之前，并排除当前用户消息作为历史证据。

`memory.mode` 的其他选项：`none` 不接受 id/text；`context` 可传 text，或选择批准的 memory id（不填默认 current）；`snapshot` 必须有对应历史快照。`memory.enabled` 缺省 true，仅控制长期文本注入，独立于近期对话、检索开关与维护开关。上下文适配器会完整放入选中文本，没有摘要裁剪；这不代表供应商上下文容量一定足够。现有 system 前言仍使用“自动维护、可修正摘要”的旧措辞，没有 HTTP 字段可改变摘要方法标注。

创建响应形状如下，省略号只用于说明，不是请求 JSON：

```text
201 {session:{id,workspace_id,title,created_at,model,memory,retrieval,
              summary,history_snapshot_id,memory_strategy,...}}
```

`session` 不返回内部 `initial/config`，但会保留你提交的 `memory.text`。`summary` 返回解析完成的 `{enabled,model,profile,max_requests,max_output_tokens}`；`max_requests` 默认30、允许0–1000，`max_output_tokens` 固定64000，实际请求还会受所选 profile 输出上限限制。disabled 时这些预算不意味着会调用维护。

提交当前消息（将 URL 中的 session_id 换成创建结果）：

```http
POST /workbench/sessions/{session_id}/chat
Content-Type: application/json

{"request_id":"00000000-0000-4000-8000-000000000001","message":"虚构示例：项目代号是什么？"}
```

`request_id` 必须是 UUID；客户端每条新提问生成一个，重试同一次提问复用。服务端按规范化 UUID 与消息原文字节的 SHA-256 判重：同 session 同键同消息返回旧 run、`reused:true`，仍为202；同键换消息409，不会重新运行失败/中断的旧 run。`message` 须非空白，存储/哈希不自动 trim。

继续同实验的新会话也调用 `POST /workbench/sessions`：

```json
{"continue_from":"example-session","title":"同实验的新会话","summary":{"enabled":false}}
```

此处 `example-session` 是需替换的虚构 ID。续会话保留 workspace、DB、记忆、原文和累计账本，只隔离近期对话；不复制旧 session 的近期消息到新 session。可覆盖主模型、检索 profile/开关及 memory/summary 的 enabled。记忆来源字段（除了 enabled）必须完全相同；summary 模型/profile/累计预算不得改变，否则409，需要新实验。新 v1 应从显式 engine=v1、memory.mode=none 的新 workspace 开始；历史上已开启 v2.6 的 workspace 具有共享发布状态，在续会话中关闭维护并不会把已有派生摘要自动恢复为8788原文。

同 workspace 的回答与维护共用锁；聊天、继续、重命名、删除遇忙返回409。重命名会 trim 标题，要求1–300字符且无控制/分隔字符；创建时仅限制字符串与长度≤300。删除是软删除，保留 DB/记忆/原文/请求产物；重复删除已删除 ID 仍200，未知 ID 为404。它不是取消或物理删除接口。

## 5. SSE、保存顺序与恢复

真实 URL 为 `GET /workbench/runs/{run_id}/events?after=0`，不是 session 级 events。普通事件没有 `event:` 行，浏览器按默认 `message` 事件处理，解析 `data.phase`：

```text
id: 5
data: {"seq":5,"time":1792713600.0,"phase":"answer_delta","root_run_id":"example-run","run_id":"example-run","session_id":"example-session","request_id":"00000000-0000-4000-8000-000000000001","parent_id":null,"tool_call_id":null,"task_id":null,"channel":"chat","data":{"text":"你好"}}

: heartbeat

```

ID 和时间均为虚构值。顶层 `seq` 为该 root run 的持久递增序号；`root_run_id` 始终对应订阅 URL。子检索/工具 observer 的 `run_id` 会另生成，`parent_id/tool_call_id` 表示关联，不可因此切换订阅 URL。正常 observer 还带 `time/channel/task_id`；服务重启合成终态事件可能没有部分 observer 字段，客户端应容忍缺省。

| `phase` | `data` 重点 / 前端含义 |
| --- | --- |
| `request_accepted`, `context_loading` | 空对象，进度提示 |
| `context_loaded` | `{stats,memory_version}` |
| `model_started` | `{model,recovery,tools_enabled}` |
| `model_thinking` | 工作台仅发布 `{status:"thinking"}`，不发布明文思考 |
| `answer_delta` | `{text}` 追加到草稿 |
| `draft_reset` | `{reason}`，清除当前草稿；工具协议纠正、工具轮或恢复轮可能使早先增量失效 |
| `model_finished` | `{finish_reason,usage,usage_missing}`；不是已保存答案信号 |
| `tool_call`, `retrieval_tool_call` | `{name,arguments,arguments_json}`，结构化工具请求 |
| `retrieval_model_started` | `{model,turn}` |
| `retrieval_tool_result` | `{name,result}`，本地搜索/读取/扩展结果 |
| `retrieval_synthesis_started` | `{model}` |
| `retrieval_handoff` | `{name,content,bounds}`；content 是交回主模型的 JSON **字符串** |
| `pro_resuming` | `{tool_call_id}`；名称为历史命名，实际主模型可以是 Sol |
| `provider_call` | 脱敏供应商记录，含 role/model/request/response/usage/events/错误及脱敏标记，开放扩展字段 |
| `answer_committed` | `{assistant_message_id}`，助手消息已提交到私有 DB |
| `answer_complete` | `{answer,result}`，完整最终答案已保存到 run，应用应以此校准草稿 |
| `maintenance_started` | 成功聊天后启用维护时发生；查看 session.summary.engine 区分方法 |
| `maintenance_published` | `{memory,result}`；旧引擎返回非 failed/error 时发出，不应仅凭事件名断言一定有新版本，检查 result/memory.version |
| `maintenance_failed` | `{error,result?}`；保留已保存回答和上一版摘要 |
| `request_failed` | `{error_type,error}`；未保存失败的助手回答，但用户消息可能已经入库 |
| `run_complete` | 正常 worker 为 `{status,answer_saved}`；重启恢复为 `{status:"interrupted",error:...}`，不保证有 answer_saved |

`answer_complete.result` 包含 `conversation_id,user_message_id,assistant_message_id,answer,tool_trace,tool_rounds,now,agent_version,context_stats,memory,maintenance,api_usage_total`。消息引用是 `chat#N` 字符串，detail.messages 的 id 则是整数；`maintenance` 在该工作台聊天路径为 null，维护结果在后续独立事件中。`api_usage_total` 是客户端账本字段 `{requests,input_tokens,output_tokens,errors}`，并不单独包含后续 summary 的独立累计额度。

顺序是先保存用户行 → 执行回答/检索 → 保存助手行 → `answer_committed` → 保存 answer.json → `answer_complete` → 可选维护 → `run_complete`。**答案完成不等于运行完成。** 旧维护会在同一 worker 继续执行并持有 workspace 锁；维护失败仍可得到 `run.status:"completed"`，因为回答已成功保存。run 完成状态为 completed/failed/interrupted；running 为正常执行中，accepted 仅为兼容已有记录的恢复判断值。没有单独的可恢复维护队列 HTTP API；工作台调用 chat 时传 `maintenance=None`，由 worker 自行后维护。

重连规则：

1. 保存已处理的最大 `seq`，重新 GET 相同 run URL，传 `?after=N`；只重放 `seq>N`。
2. 若有非空 `Last-Event-ID` 头，它优先于 query；必须可解析为非负整数，否则400。浏览器 EventSource 自动带头时要考虑此优先级。
3. 若 cursor 超过服务端现有序号，先收到特殊帧 `event: reset`，其 data 为 `phase:"replay_gap",seq:0,data:{reason:"cursor_ahead",reset_after:0}`，没有普通 `id:` 行。注册 reset 监听，清空本地流状态后接收从0回放的事件。
4. 无新事件时约每秒发送 `: heartbeat` 注释。读到持久的 `run_complete` 后关闭连接；客户端处理终态后主动关闭 EventSource，避免自动重连循环。若 after 已包含终态，连接也会结束，必要时 GET run 状态确认。
5. 服务重启将登记中的 running/accepted run 标为 interrupted 并追加终态，不自动重发模型请求；新旧事件仍可按磁盘序号重放。不要把重启后的 replay 当成恢复推理。

`/wire` 与 `/artifacts` 都只返回 run 和 wire_events，不能假定提供 answer/summary 文件下载。reasoning 与凭据在持久记录中脱敏，`record_changed/replay_limited/redactions` 说明不可逐字回放；工具证据和普通上下文仍可能保留全文。

## 6. 批量 plan / start / results / report / resume

`suite` 核心字段为 `models:[完整profile]`、`questions:[{id,text,checks?}]`、`contexts:[...]`、`budgets:{max_requests,trial_max_requests,max_input_tokens}`。`version` 缺省1，`now_epoch` 缺省为每次请求当时的时间，`repeats` 为1–100、`concurrency` 为1–16；模型/问题/材料各组1–100项且组内 ID 唯一，笛卡尔积最多10000案例。checks 仅含 `contains/not_contains` 非空字符串列表，不是语义质量分数。

| context.mode | HTTP 材料字段与含义 |
| --- | --- |
| `none` | 仅 `{id,mode}`；不接受记忆、近期种子或 inject_memory 字段 |
| `context` | `{id,mode,text?或memory_id?,recent_seed?,inject_memory?}`；不指定材料时 current；固定全文且禁用检索 |
| `snapshot` | 批准的 `memory_id`（缺省 current），可有 recent_seed/inject_memory；冻结摘要和历史，但禁用检索 |
| `pipeline` | 同 snapshot，启用真实检索 Agent；suite 必须有固定 `retrieval_profile` |

仅当有 pipeline 材料时才能且必须提供 `retrieval_profile`。HTTP 不接收 evaluator 内部 `file` / `snapshot` 路径；不提供任意文件读取。snapshot/pipeline 不接受 text，故不能在当前批测 HTTP 中直接组合“自定义8788全文 + pipeline检索”；聊天会话接口可以，见第4节。summary 开启时，部分 current/context 计划会被物化为 snapshot 以保留原始消息 ID；这属于旧引擎行为。

`recent_seed` 可以是按时间排序的 `{id?,role:"user"|"assistant",content,created_at}` 数组，每条时间严格小于 now_epoch；在 snapshot/pipeline 中也可为 `"snapshot"` 或 `{instance,conversation_id,limit?}`。`chat` 可指定 `recent_limit/recent_token_budget` 非负整数。none 材料始终无近期种子。pipeline 的不同主模型可能提出不同查询，即使检索 profile 相同也不保证最终证据相同。

完整可复制的最小 batch 请求见 OpenAPI 的 `planBatch/startBatch` example（单个 Sol/high、none材料、summary关闭）。浏览器中可按下面方式组装，不含真实问题或凭据；`solProfile` 为第4节的完整 Sol 对象，代码仅为接入示例，不在归档过程执行：

```javascript
const body = {
  suite: {
    models: [solProfile],
    questions: [{id: "q1", text: "虚构示例：只回答你好。", checks: {contains: ["你好"]}}],
    contexts: [{id: "plain", mode: "none"}],
    repeats: 1,
    concurrency: 1,
    budgets: {max_requests: 6, trial_max_requests: 6, max_input_tokens: 120000}
  },
  summary: {enabled: false, profile: solProfile}
};
```

先 POST `/batches/plan` 查看 `valid,missing_credentials,runtime_auth_unchecked,cases,concurrency,now_epoch,per_trial_request_ceiling,batch_request_ceiling,summary,context_modes,warnings,api_calls`。`api_calls` 为0，但 plan 会写本地 suites/快照，因此不是完全无写入的查询。它只检查 API Key 环境是否有值，不验证凭据可用性；订阅保持 runtime_auth_unchecked。

start 提交同形 body 到 `/batches`，**不接受 plan_id**，会重新规划和冻结当前输入。若需要可比较输入，请显式固定 now_epoch、profiles 与批准快照；先前 plan 不锁定之后 start 的 source。主模型+检索的单案例请求上限为两个 request budget 的较小值，batch_request_ceiling 是乘案例数的展示上限；summary 若启用则独立计额，每个案例私有 workspace 累计上限另计。

start 返回202 `{batch}`，batch 含 `id,status,created_at,plan,summary,previous_id`，完成时增加 finished_at，失败可能有安全 error。轮询 batch detail：`manifest` 在初期可为 null，`results` 是已落盘记录按 index 排序，无分页。外层 batch 完成值是 `completed`，内部 manifest 是 `complete`；案例 status 为 `passed/failed/error`，前两个仅指字面检查。案例详情返回完整 answer/checks/tool_trace/usage/耗时/材料标识/parameters/chat? 等，另含 `wire_events` 和 `summary`（未维护时可 null）。

report 是 HTML，会随案例增量生成；报告已存在不等于批次结束。`previous_id` 用于已有 results.json 的批次比较，并不强制旧批 status=completed。比较报告并非人工效果验收。

resume 请求必须只有 `{concurrency:1..16}`，不能换模型、材料、问题或预算。running 批次409；其他状态进入续跑，使用归档物化输入并核对输入 hash/案例 identity。保留已有结果，包括 failed/error；只补尚无结果的案例，归档未完成目录并保留累计花费。它不是“重试所有失败案例”。缺失物化输入等本地文件可能在202前500；后台恢复校验失败则保存 batch.failed/error。服务启动会将未完成批次根据 manifest 标为 completed/interrupted，但不自动续跑。没有批次 SSE 或 HTTP取消端点。

## 7. 新工具可直接复用的 Python 入口

以下是现有函数签名与返回边界，不要求复制旧 HTTP 工作台，也不重复全文 prompt。新工具自行准备隔离的 Config/数据库/客户端；这些函数不是无状态纯函数。保留主模型与检索模型独立客户端，显式传入各角色profile；不要依赖函数缺省client后的旧路由。下方Sol/high只是示例。

`summary_store.Published` 是**全文/版本元数据适配对象**：`Published(present, version=0, text="", published_at=None, now_max=None, summary_path=None, memory_path=None, user_id=None, reason="")`。`display_text` 在 present 为 false 时提供“尚无记忆”提示。直接构造 `Published(True, text=完整8788摘要)` 即可给当前上下文和检索适配，不需要从 v2.6 publisher 加载，也不要求继续 v2.6 算法；版本号是适配元数据，不证明生成方法或事实核验。当前上下文构造器仍会附加旧 system 前言，若重建工具要调整措辞，应在后续实现中明确处理，本轮不改动。

| 实际入口 | 必需参数与关键可选参数 | 返回与副作用 |
| --- | --- | --- |
| `chat.chat_agentic(config, conn, message, *, published, instance="trial", recent_limit=None, recent_token_budget=None, max_tokens=None, conversation_id=None, maintenance=None, stream=False, client=None, retrieval_client=None, now_epoch=None, allow_memory_tools=True)` | `conn` 为已初始化隔离 DB 连接；published 传完整8788文本；conversation_id 显式固定；client 为主角色，retrieval_client 为检索角色；v1 `maintenance=None`，stream 按需 | 返回 ChatResult：conversation_id、两个 chat#N、answer、tool_trace、tool_rounds、now、agent_version、context_stats、memory(present/version)、maintenance、api_usage_total。先写 user，成功后写 assistant 并提交；失败可留 user，不能认为函数回滚整轮。调用真实模型；stream 增量通过当前 Observer 发送，返回本身不是 generator |
| `agents.memory_agent_search(config, conn, published, query_text, *, instance="trial", client=None, max_rounds=None, now_epoch=None, delegation=None, exclude_chat_ids=(), conversation_id=None)` | query_text 可为空；结构化 delegation 包含 gaps/question/keywords/entities/time_hint/known；函数补 now_iso、当前会话近期上下文与有界 memory_excerpt。显式传检索 client、conversation_id、当前消息排除 ID | 返回检索 trace，并增加 query、queries、sufficient（found/partial）、rounds。独立检索子角色，不生成最终用户回答、不维护摘要；会调用模型并读取历史。`max_rounds` 缺省走4轮工具预算 |
| `memory_agent.run(config, conn, instance, delegation, now, *, client=None, max_tool_turns=4, exclude_chat_ids=())` | 更低层的独立检索循环；now 是 epoch；delegation 是结构化任务，可自带 session_context/memory_excerpt/now_iso；不自动做上一入口的完整委托组装 | 返回 status(found/partial/not_found)、findings、evidence、gaps、expandable、note、sources、steps、n_tool_turns、engine、now、retrieval_stats、n_sources。最多工具轮后另有一个无工具 JSON 综合请求；检索只读本地历史，模型/用量记录仍有写入 |

`chat.chat_agentic` 若省略 retrieval_client 会回落到主 client；分角色配置应显式传入。`maintenance=None` 只关闭 chat 函数的维护入队；旧 workbench worker 自己的后维护由 session.summary.enabled 控制，所以走 HTTP 时还必须将 summary.enabled 设为 false。新工具若直接调用该函数且不另接旧 summary worker，就没有旧维护。

最小适配示意（不执行；config/conn来自新工具自己的隔离工作区；main_profile与retrieval_profile是各角色选定的完整配置，格式同第4节，二者可不同）：

```python
from continuity import chat
from continuity.providers import create_client
from continuity.summary_store import Published

published = Published(present=True, text=full_8788_summary)
main_client = create_client(config, main_profile, role="main")
retrieval_client = create_client(config, retrieval_profile, role="retrieval")
result = chat.chat_agentic(
    config, conn, "虚构示例：项目代号是什么？",
    published=published, instance=config.instance,
    conversation_id="example-new-tool-session",
    client=main_client, retrieval_client=retrieval_client,
    maintenance=None, stream=False, allow_memory_tools=True,
)
```

这里新工具对外可只接收 text，然后由服务端构造 system+user 统一 Responses 请求；不能把外部消息 text 直接变成无角色的供应商 input，也不能把 summary.enabled 当作8788维护实现。

检索实现读取该 conn 内 messages 的选中分支/非思考内容，以及当前 instance 的 user/assistant chat_log；均早于 now，排除指定当前 chat ID。会过滤泄漏工具序列化的助手文本，保留原行不删除。findings 的 kind 标记 user_fact/assistant_context/inference/state，含来源验证；evidence 从原文物化而非模型重写。低层 trace 最多14条证据、每条4000字符；交给主模型的 `retrieval_handoff.content` 再限制8条、每条3000字符并保留 truncated 标志。不要把 trace 和主模型收到的 handoff 当成相同大小的证据全文。模型推断仍不是事实保证。

## 8. 已确认缺口与归档核对

- **v1 写入更新**：初始化、追加和稳定层刷新及版本读取已接入，见[摘要写入 API](摘要写入API.md)。任意全文替换/回滚、HTTP取消和跨设备合并不在本轮实现范围。
- **来源/方法元数据缺口**：自定义摘要不绑定可选 source ID/hash；HTTP 不能指定任意历史库，不能证明8788摘要与当前 source一致，也不能更改旧 context 前言的方法标注。新工具需要由自己的适配层明确管理来源。
- **取消缺口**：聊天、检索、维护、批次均无 HTTP cancel；断开SSE/关闭页面不取消，删除忙会话返回409。重启只标中断，不恢复进行中的生成。
- **恢复与操作缺口**：聊天 request_id 是幂等复用，不是失败重试；无单独维护重试入口。批次 resume 只补无结果案例；plan 没有可绑定的 plan_id；无批次事件流或结果分页。
- **部署与凭据缺口**：loopback/同源，无远程鉴权或多用户隔离；无 credentialsref 字段；订阅模型目录自动发现不支持。模型能力与认证只在真正调用时验证，本轮不作在线可用性承诺。
- **批测组合缺口**：pipeline 只接受批准快照材料，不能直接传入自定义8788文本；聊天创建接口支持自定义全文加检索。

源归档记录曾做静态核对；本次只做本资料副本的 JSON 解析、内部 `$ref` 和本地文档链接检查，没有重新进行源码路由审计、运行测试或发送接口请求。原验收文件未带入，不能将旧结论当本包验证。OpenAPI 中开放的供应商/维护结果/上下文统计对象保留扩展字段，避免把非稳定内部结构误作封闭公共协议；核心请求字段、响应信封、事件格式与状态码以实际代码为准。
